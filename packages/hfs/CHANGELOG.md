# Changelog

## 6.2.4 - 2026-11-08

- Changed: `HFS_CANON_PIN_DRIFT` is report-only in `app check --env local` for a pin whose exact version the app's lockfile resolved from a registry on this machine (`starci deps install-local`), not for a spec that spells `-local.<n>`: `deps publish-local` publishes the version committed in git, so a local build has no distinguishing version. A range pin, or the same version resolved from npm, is a real drift.
- Changed: the verb catalog (`runtime/packages/cli/src/catalog.generated.mjs`) carries the texts of `deps publish-local`, `deps install-local` and `deps check` of CLI 1.1.0-alpha.93.

## 6.2.3 - 2026-11-08

- Fixed: the Sonar scan of `starci app check` on a server without branch support (Community) no longer reads the main project first. A derived project `<key>-local` the token can analyse (`api/qualitygates/project_status` answers 200, which a project analysis token may read) is scanned as it is, with no read of the main project and no gate binding; only a missing derived project is created, which needs the token to read the main project and to create projects and select a gate, and without that the scan is skipped naming the remedy (create `<key>-local` and bind it to the gate, or give the token Create Projects). The gate digest of the scan key falls back to the gate's name when the token cannot read its conditions, and to no reuse when it reads neither: the scan still runs. The verdict of the derived project's gate is read with the scan's own token. Specs: `src/check-cache-sonar-scan.spec.mts`.

## 6.2.2 - 2026-11-08

- Added: `starci app check --env local|prod` (default `local`). Both environments judge the same code checks (hfs, format, db, wiring, lint, types, tests, coverage, build, audit stay identical and blocking; a lint, type or test error is red in both). They differ only in the findings about whether the run is fit to commit, push or release: the codes marked `localOnly: true` in `modules/kernel/failure-codes.yaml` (`HFS_CANON_PIN_DRIFT` of a pin naming a `<version>-local.<n>` build, `HFS_CHECK_CACHE_UNPORTABLE` of a local-registry install without a source digest) are listed `LOCAL, REPORT ONLY` and never red in `local`, and the run ends `gate: green for local (not pushable)` when only they remain; `prod` blocks them. The one list is `runtime/scripts/hfs/check-env.mts`; a producer marks the instance a local-registry build alone causes (`local: true`). The managed `.husky/pre-push`, `ci.yml` and `cache-verify.yml` templates and the release gate's `app-check` row run `--env prod` (run `app sync --execute`). Specs: `src/check-env-source-key.spec.mts`, `src/check-gates-parser.spec.mts`, `src/release-cache-verify-lock.spec.mts`.
- Changed: the check cache keys a harness or tool package on its source. A package packed by `release publish` or `deps publish-local` carries `starciSource` (the digest of its tracked source files) in its manifest; the `hfs` and `pkg:@starci/*` fingerprint parts, the install digests of a record's reads and the lint import graph use it in place of the version and integrity when present, so the `-local.<n>` build and the npm build of one commit yield identical keys and the records of a run on the local build stay valid after `deps install-local --restore`. A local-registry install whose package carries the digest is portable; one without it, and a linked or copied folder, is not.
- Changed: `HFS_DEV_BRANCH_MISSING` (a whole `app check` of an app repository with no `dev` branch, locally or on origin) is an error in both `--env local` and `--env prod`, and PROJECT-BRANCH-1 says an app must keep `main` and `dev`. The managed pre-push hook keeps one bootstrap path: the first push into an empty remote must push `main` and `dev` together at the same commit; `main` alone is refused `BRANCH_MAIN_NOT_ON_DEV`. Specs: `src/dev-branch.spec.mts`, `src/pre-push-branches.spec.mts`.
- Added: the export `@starci/hfs/tool-cache` (`toolCacheDir`), the untracked tool cache of an app, which the CLI's `deps install-local` keeps its record in.

## 6.2.1 - 2026-11-08

- Changed: `app check` starts its critical path first. Each step of `CHECK_GRAPH` declares a static `priority` (the unit run, then lint, the structure pass, tsc, wiring, the rest); ready steps start highest first, and a child asks the governor, and takes its lanes, only once every ready or running step of a higher priority has had a child admitted, has ended or `LAUNCH_WAIT_MS` passed. Specs: `src/check-schedule.spec.mts`.

## 6.0.3 - 2026-11-07

- A patch: `app check` keeps what it has judged while it runs. Every family's records are journaled the moment the family finishes, and inside a family the types family journals each program, the test family each spec's coverage as the reporter writes it, and the lint family each batch of 250 files the ESLint list runner judged (the child appends them to the journal file the family opens for it).
