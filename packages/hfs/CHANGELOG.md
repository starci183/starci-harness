# Changelog

Versioned history starts at beta; earlier history is in git.

## 6.17.22 - 2026-11-28

- Changed (h-ssh-gate-docker, `stack/ssh-gate.mts`, `stack/backup-ops.mts`, `stack/manager-backup.mts`): a CI key behind the forced-command gate (`VPS_GATE: "1"`, STARCI_SSH_GATE=1) deploys a whole release, migrations included. The edge preflight (`edge-alias.mts` `edgeCollisions`), `stack jobs` and `stack task` run docker through the docker CLI of the run (DOCKER_HOST=ssh://<alias>, the dial-stdio the gate admits), never a shell over ssh, so a gated deploy no longer stops at STACK_DEPLOY_EDGE_UNREADABLE; `jobs` and `task` now open the docker transport like `deploy`. The manager backup of a `database.target: stack` database is four named operations of the gate, `db-dump`, `db-receipt`, `db-measure` and `db-decrypt`, each confined to `<backup dir>/<project>-<stamp>.tar.age` and its receipt and each argument of a closed alphabet (`backup`, `container`, `ident`, `recipients`); the owner's ungated key runs the same bodies under `sh -c`. The receipt now travels as one base64 line. Install the new gate on every gated manager: `starci app stack ci-key --env <env> --print-gate` (the text changed).
- Added (h-ssh-gate-docker, `src/stack-ssh-gate-deploy.spec.mts`): two deploys (the first start, then expand and contract migrations with the manager backup), a rollback, verify, seed, jobs and task run under STARCI_SSH_GATE=1; every command they send over ssh goes through the generated gate under sh and is admitted, and every docker command ran on the runner.

## 6.17.21 - 2026-11-28

- Fixed (h-deploy-secrets, `sync/stack-images.mts`, R251 `rules/deploy-workflow.mts` `stackDeployCaller`): every `deploy-<env>` job of ci.yml calls stack-deploy.yml with `secrets: inherit`, and the images call does whenever a sealed image job exists. A called workflow reads only the secrets its caller passes, an Environment secret of its bound job included, so the deploy job of a release read `SOPS_AGE_KEY` empty (`SOPS_AGE_KEY is explicitly empty or invalid`) though the production Environment held it. The bound job still reads its Environment's key, which wins over the repository's. R251 now requires the inheritance on a stack-deploy.yml call (`calls stack-deploy.yml without secrets: inherit`) and refuses it on any other. Run `starci app sync`.
- Fixed (h-deploy-secrets, `runtime/engine/secrets.mts` `inlineAgeIdentity`, `runtime/scripts/api/sops/lib.mts`): an inline `SOPS_AGE_KEY` may be the bare `AGE-SECRET-KEY-1...` line or one identity document as age-keygen writes it (keys.txt with its `# created:` and `# public key:` comments, CRLF or LF), the form a CI secret is often pasted in. The selected invocation hands age and sops the bare line. It refused the document as `inline-context-unqualified` before any sops process ran, so `starci app stack connect` could not open the transport member of a release deploy (STACK_SECRET_MEMBER_UNREADABLE); every stack read of a member (connect, deploy, render, migrate, rollback, seeds) goes through that one seam. A value with no identity line is now refused `invalid-inline`, naming the form; the secret names are versioned from the bare line, so both forms keep the same Swarm secret names.

## 6.17.20 - 2026-11-28

- Fixed (h-deploy-age-path, `sync/stack-images.mts` `installAgeSteps`): the "install age" step of `stack-deploy.yml` (deploy, rollback) and of the sealed image jobs of `images.yml` ran `age --version` and `age-keygen --version` by bare name in the same step that appends `$RUNNER_TEMP/age-bin` to `$GITHUB_PATH`. A `GITHUB_PATH` entry reaches only the later steps of the job, so the step stopped with `age: command not found` (exit 127) and no release tag could deploy. The step now proves both binaries by their absolute path (`"$RUNNER_TEMP/age-bin/age" --version`) and still appends the folder to `GITHUB_PATH` for the later steps; ci-pipeline.spec refuses a bare `age` call in that step. Run `starci app sync` to rewrite the app's managed workflows.

## 6.17.18 - 2026-11-27

- Fixed (h-json-embedded-source, `runtime/scripts/lib/secret-patterns.mts`): the `assigned-secret` heuristic reads a JSON file's strings decoded. Source code a JSON string carries (a generated seed embedding a module's text) is judged as source: an unquoted `secret: NAME` is a reference when that same string declares or imports `NAME`, so a seed's `secretField: SIGNER_FIELD` no longer refuses a push; a quoted literal written `\"...\"` inside the string is now decoded and refused, and an undeclared unquoted value or a dotenv text carried in a string stays a candidate.
