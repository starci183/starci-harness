# packages

The packages StarCi apps install from npm: the quality canon, the Grammar and its lint families, the app implementation behind `starci app`, the shared front-end and back-end libraries, and the AI pool router. Each folder is its own npm package: install, build and test it inside its folder (`npm ci`, `npm run build --if-present`, then `npm test`). A spec may read a sibling package's fixtures or source by relative path (`../eslint-canon-be/fixtures/...`, `../eslint-canon-fe/src/index.ts`, `../grammar/src`), and a package whose published dependency is a sibling of this folder installs that sibling as a `file:../<name>` dev dependency under `install-links=true` (its `.npmrc`), so npm copies it instead of linking it; install and build the siblings a package needs before testing it, deps first (npm packs a `file:` copy from its sibling's folder, so the sibling's `dist/` must exist first); `starci release affected` lists that build order per package.

`@starci/hfs/runtime/` is the one runtime of the app laws (the slot manifest, the rule catalog, the canon pins, the failure codes, the architecture machine): its canonical code is `hfs/runtime/**/*.mts`, built to `.mjs` by the HFS build. `eslint-canon-be`, `eslint-canon-fe`, `eslint-grammar-core` and `eslint-grammar-offset-pop` read it at run time from the installed `@starci/hfs` (`@starci/hfs/runtime/*`, their `RUNTIME_ROOT`), which they peer by a same-minor range, and bundle no copy of it: an hfs data change releases hfs alone. A canon's own `runtime/` keeps only the files hfs does not ship (its project graph rule, the jsdoc, sonar and next helpers, the knowledge grammar-core cites), listed under `own` in its `runtime/bundle.json`; `node scripts/sync-bundles.mjs --check` in `hfs` keeps that list true. The canon pins name each `@starci` package by its folder here (`source: packages/<name>/package.json`) at that folder's version, or a same-minor `range` for the Grammar family and the two canons (`packages/hfs/src/canon-pins.spec.mts` holds both). The CLI is not pinned there: an app's `starci-harness` is the version of the CLI that runs `@starci/hfs` (`runtime/scripts/hfs/canon-pins.mjs`), since the CLI depends on `@starci/hfs` exactly.

## Grammar family versions

`grammar`, `eslint-grammar-core` and `eslint-grammar-offset-pop` always have the identical full release version, including the patch. A metadata-only change to a lint family releases all three together; unchanged component code is rebuilt with the new version stamp. The family equality spec in `eslint-grammar-core/src/index.spec.ts` enforces this release contract. A patch releases the family alone: the canon pins give it a same-minor range (`range: ~x.y.z` beside `version` in `hfs/runtime/knowledge/hfs/canon-pins.yaml`), which R15 and the release's sibling judgement accept, so `@starci/hfs`, the canons and the CLI do not move; a minor raises that range and releases the whole family. Which one a change is, and the release check that refuses a patch carrying a minor's change, is [contexts/grammars/contributing.md](../contexts/grammars/contributing.md) "Patch or minor".

## Build convention

Every package is TypeScript source built to JavaScript in `dist/`; no package ships hand-written JavaScript or a hand-written `.d.ts`.

- **Source.** Code lives in `src/` as `.ts` and imports a sibling file by its `.ts` name (`./scope.ts`); the build rewrites the specifier to `./scope.js`: tsc does it in the JavaScript, and a package whose source imports `.ts` follows `tsc` with the declaration step that does it in `dist/**/*.d.ts` (ai-router's `build` is the reference; it uses `\x22`, never `$1` or `\"`, so sh and cmd read it alike). CI refuses a built declaration that still names a `.ts` file. Data that is input, never compiled (lint fixtures, CSS fixtures, app templates, YAML, the bundled `runtime/` copies), stays outside `src/` and is shipped or copied as it is. An untyped module the code imports (a `runtime/` copy, a sibling not yet converted) is typed by one ambient declaration file in `src/`, never by `any` or a suppression.
- **tsconfig.** `tsconfig.json` extends `@starci/tsconfig/package-esm.json` (ES modules) or `@starci/tsconfig/package-cjs.json` (a package jest or prettier loads with `require`: `jest-preset`, `prettier-config`), sets `noEmit` and includes `src` with its specs; it is the `typecheck`. `tsconfig.build.json` extends it, turns emit on and excludes the specs. The presets hold every strictness flag and anchor `rootDir` at `src/` and `outDir` at `dist/`, so a package config restates neither, except a CommonJS package, whose `tsconfig.json` sets `rootDir: "."` to typecheck `test/` beside `src/` and whose `tsconfig.build.json` sets it back to `src`. `@starci/tsconfig` is a `file:../tsconfig` dev dependency.
- **Build.** `npm run build` removes `dist/` and runs `tsc -p tsconfig.build.json` (then generates or copies the package's data, if it has any). `prepack` runs `build`, so `npm pack` and `npm publish` always ship a fresh `dist/`.
- **Manifest.** `main`, `types`, `exports` and `bin` point into `dist/`, every public specifier unchanged, and `files` ships `dist/` plus the generated or bundled data the code reads, nothing from `src/`.
- **Specs.** A spec is `*.spec.ts` and `npm test` runs `typecheck` first. An ES-module package keeps its specs beside their subjects in `src/` and runs them on the source: Node strips the types, which is why the source holds only erasable syntax (`verbatimModuleSyntax`, `erasableSyntaxOnly`). A CommonJS package compiles `export =` and `import` to `require`, which Node cannot run from source, so its `test` builds first and its specs (in `test/`, an ES-module folder) load the built `dist/` the way jest or prettier does. A package with nothing to build (`tsconfig`) keeps its spec at its root.
- **Paths.** A file found through `import.meta.url` or `__dirname` is resolved from the package root, which sits one level above both `src/` and `dist/` at the same depth, so one relative path works from the source and from the build.
- **CI.** `.github/workflows/ci.yml` tests each package a change affects in its own job, after installing and building the siblings it needs (`starci release affected`), and refuses a built declaration that names a `.ts` file.

- `eslint-canon-fe` (`@starci/eslint-canon-fe`): the universal front-end ESLint canon (`starciFeConfig`, `loadHfs`) for TypeScript and Next.js; consumed by the `fe/eslint.config.mjs` of every StarCi app, beside its Grammar family config.
- `eslint-canon-be` (`@starci/eslint-canon-be`): the back-end ESLint canon (`starciBeConfig`, `loadHfs`) for Nest; consumed by the `be/eslint.config.mjs` of every StarCi app.
- `grammar` (`@starci/grammar`): the Grammar an app's UI is drawn in: the Common contract and the two families `core` and `offset-pop`, each with its root and stylesheet; consumed by every StarCi front end.
- `eslint-grammar-core` (`@starci/eslint-grammar-core`): the `core` family's lint factory (`coreGrammarConfig`) over the Grammar component API, with `@starci/eslint-canon-fe` as its peer; its release follows the Grammar family version contract above.
- `eslint-grammar-offset-pop` (`@starci/eslint-grammar-offset-pop`): the `offset-pop` family's lint factory (`offsetPopGrammarConfig`), inheriting the core checks, with `@starci/eslint-grammar-core` as its peer; its release follows the Grammar family version contract above.
- `stylelint-canon` (`@starci/stylelint-canon`): the CSS canon (Grammar tokens only, brand values only in `brand.css`); consumed by the `stylelint.config.mjs` of StarCi front ends.
- `heroicons` (`@starci/heroicons`): the glyphs `@heroicons/react` lacks, drawn in its style; imported by StarCi front ends.
- `event-stream` (`@starci/event-stream`): the server-sent-events client (Bearer renewal, Last-Event-ID resume, backoff, heartbeat, an SWR adapter); one instance per front end.
- `next-data` (`@starci/next-data`): the data helpers of a front end over SWR, pure logic and one middleware with no component: `pollingRestart` (a function `refreshInterval` that stopped at 0 starts again for newer data), the viewer and tenant key helpers, `viewerSwrConfig` (the viewer-keyed cache config) and `createViewerCache` (the writes that reach the viewer's cache); each operation's SWR hook stays in the app.
- `auth` (`@starci/auth`): the lite sign-in in one package: `./server` (the NestJS module `AuthModule.register` / `registerAsync`: EdDSA access tokens with a multi-key JWKS, bcrypt passwords, Google OAuth with state and PKCE, rotating refresh sessions with a reuse grace window and reuse detection, a failures-only sign-in limit, the refresh cookie), `./client` (the front-end client with the access token in memory, one shared refresh and sign-out only on 401 or 403) with `./client/react` (provider and hooks), `./contracts` (door paths, wire codes, claims) and `./testing`; it ships the session-table migration (`migrations/identity-sessions.sql`) and is the only importer of `passport*`, `jose`, `bcryptjs` and `@nestjs/jwt`, reached by an app through `integrations/passport` and `modules/auth`; its `npm test` also typechecks and lints, and fails under 90% line coverage.
- `auth-oidc` (`@starci/auth-oidc`): the full-edition sign-in, the OIDC client of the identity provider (Keycloak) behind the same `PrincipalVerifier` interface as `@starci/auth`: `./server` (the NestJS module `OidcModule.register` / `registerAsync`: issuer discovery, the provider's JWKS with caching and rotation, algorithm-pinned token checks, role mapping, the authorization code flow with S256 PKCE, state and nonce, no environment read), `./client` (PKCE redirect, callback, one shared refresh, tokens in memory, sign-out only when the provider ends the session), `./contracts` and `./testing` (`FakeOidcIssuer`: discovery, JWKS, token minting and outage injection, so an app tests without Keycloak); it is the only owner of `jose` in a full app, reached by a back end only through `integrations/keycloak`; its `npm test` also typechecks (isolated declarations) and lints, and fails under 90% line coverage, and it needs `@starci/auth` built beside it for the interface-compatibility specs.
- `hfs` (`@starci/hfs`): the implementation behind `starci app` (scaffold, sync, check, stack, db, codemod) for one product repository, run in-process by the harness CLI (`starci-harness`, `cli/`), which is the command line a product installs; `@starci/cli`, the app CLI that used to run it, is retired.
- `tsconfig` (`@starci/tsconfig`): the strict TypeScript presets `base`, `be`, `build`, `next` and `e2e`; extended by the tsconfig files of every StarCi app's back end and front end.
- `prettier-config` (`@starci/prettier-config`): the one Prettier config; consumed by every StarCi app's `prettier` setting.
- `jest-preset` (`@starci/jest-preset`): the jest config of a Nest repository and the shared unit-test double kit; consumed by the jest config and unit specs of StarCi back ends.
- `test-world` (`@starci/test-world`): the shared e2e world of every StarCi back end; pairs exactly with `@starci/jest-preset`.
- `nest-kit` (`@starci/nest-kit`): the building blocks of a back end that no capability owns: `classifyFailure(cause, DomainError)` (the class of a flow failure, BE-RESILIENCE-2, the one rule the job runner and both event consumers apply) and the module definition: `defineConfigurableModule<Options>()` (a sub-module, feature, transport or cli group) and `defineCapabilityModule<Options>(settings?)` (the representative module of a capability, with `isGlobal`), each returning the module base class, the options token and the options types with their types stated, so every `<x>.module-definition.ts` is one call that R368 and R21 both accept; a runtime dependency of every StarCi back end; its `npm test` also typechecks and lints, and fails under 100% line coverage.
- `next-i18n` (`@starci/next-i18n`): the next-intl stack of a front end, generic over the app's locales and with no component: `defineI18n` (the typed description of the languages), `createProxy` (the locale-negotiating proxy), `createI18nNavigation`, `createRequestConfig` (loads the app's own catalogs) and `createReadLocaleSegment` (the `[locale]` layout's locale read); the app keeps its message catalogs and calls none of next-intl's own stack builders.
- `object-storage` (`@starci/object-storage`): object storage over S3-compatible storage (MinIO in lite): a NestJS module (`ObjectStorageModule.register` / `registerAsync`) and the `ObjectStorage` port (presigned PUT and GET that sign the content type and size, head, get, put, list, delete, bucket setup, size and content-type limits, coded errors), no environment read, and `@starci/object-storage/testing` (the same checks over memory); the only owner of `@aws-sdk/client-s3` and `@aws-sdk/s3-request-presigner`, imported by an app only in `integrations/object-storage`.
- `mail` (`@starci/mail`): outgoing mail over SMTP: a NestJS module (`MailModule.register` / `registerAsync`) and the `Mailer` port (`send({ to, message })`) with connect, greeting, socket and total timeouts, STARTTLS required by default, recipient, message and attachment checks, a shared SMTP target policy (`assertSmtpTarget`), coded errors, typed escaping render helpers returning `{ subject, text, html }`, no environment read, and `@starci/mail/testing` (an in-memory outbox with the same checks); the only owner of `nodemailer`, imported by an app only in `integrations/mail`.
- `ai-router` (`@starci/ai-router`): one router engine (`createRouter`, `@starci/ai-router/gateway`) behind a NestJS module (`AiRouterModule.register` / `registerAsync`, the injectable `AiRouterService`) and an OpenAI-compatible gateway with virtual API keys (issued and stored, or mounted from a secret the app holds), quotas and per-key usage (`AiRouterGatewayModule`, or the process entry `dist/gateway/run.js serve|keys` driven by `@starci/ai-router/cli`; no package bin, the CLI is one). It routes OpenAI-compatible `chat`, `stream` and `embeddings` calls across many providers by kind (Anthropic through a Messages adapter, OpenRouter, Qwen, DeepSeek, OpenAI, Gemini, Groq, any OpenAI-compatible endpoint), each with an array of keys read from env (`poolFromEnv`), with a persisted blacklist for spent quotas and refused secrets, breakers, rate-limit awareness, failover by profile, pinned embeddings and redacted telemetry, and `@starci/ai-router/testing` (the fake provider and `AiRouterTestingModule`) for consumers' tests; its `npm test` also typechecks and lints, and fails under 90% line coverage.
