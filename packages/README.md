# packages

The packages StarCi apps install from npm: the quality canon, the Grammar and its lint families, the app implementation behind `starci app`, the shared front-end and back-end libraries, and the AI pool router. Each folder is its own npm package: install, build and test it inside its folder (`npm ci`, `npm run build --if-present`, then `npm test`). A spec may read a sibling package's fixtures or source by relative path (`../eslint-canon-be/fixtures/...`, `../eslint-canon-fe/src/index.ts`, `../grammar/src`), and a package whose published dependency is a sibling of this folder installs that sibling as a `file:../<name>` dev dependency under `install-links=true` (its `.npmrc`), so npm copies it instead of linking it; install and build every package, in folder order, before testing any (npm packs a `file:` copy from its sibling's folder, so the sibling's `dist/` must exist first).

A package's `runtime/` is committed source, edited in place. `eslint-canon-fe`, `eslint-canon-be`, `eslint-grammar-core`, `eslint-grammar-offset-pop` and `hfs` each bundle copies of the same runtime files (the canon pins, the Grammar catalog, the slot manifest and the architecture machine); a change to one copy is made to every copy in the same commit, and the pins name each `@starci` package by its folder here (`source: packages/<name>/package.json`) at that folder's version.

## Build convention

Every package is TypeScript source built to JavaScript in `dist/`; no package ships hand-written JavaScript or a hand-written `.d.ts`.

- **Source.** Code lives in `src/` as `.ts` and imports a sibling file by its `.ts` name (`./scope.ts`); the build rewrites the specifier to `./scope.js`: tsc does it in the JavaScript, and a package whose source imports `.ts` follows `tsc` with the declaration step that does it in `dist/**/*.d.ts` (ai-router's `build` is the reference; it uses `\x22`, never `$1` or `\"`, so sh and cmd read it alike). CI refuses a built declaration that still names a `.ts` file. Data that is input, never compiled (lint fixtures, CSS fixtures, app templates, YAML, the bundled `runtime/` copies), stays outside `src/` and is shipped or copied as it is. An untyped module the code imports (a `runtime/` copy, a sibling not yet converted) is typed by one ambient declaration file in `src/`, never by `any` or a suppression.
- **tsconfig.** `tsconfig.json` extends `@starci/tsconfig/package-esm.json` (ES modules) or `@starci/tsconfig/package-cjs.json` (a package jest or prettier loads with `require`: `jest-preset`, `prettier-config`), sets `noEmit` and includes `src` with its specs; it is the `typecheck`. `tsconfig.build.json` extends it, turns emit on and excludes the specs. The presets hold every strictness flag and anchor `rootDir` at `src/` and `outDir` at `dist/`, so a package config restates neither, except a CommonJS package, whose `tsconfig.json` sets `rootDir: "."` to typecheck `test/` beside `src/` and whose `tsconfig.build.json` sets it back to `src`. `@starci/tsconfig` is a `file:../tsconfig` dev dependency.
- **Build.** `npm run build` removes `dist/` and runs `tsc -p tsconfig.build.json` (then generates or copies the package's data, if it has any). `prepack` runs `build`, so `npm pack` and `npm publish` always ship a fresh `dist/`.
- **Manifest.** `main`, `types`, `exports` and `bin` point into `dist/`, every public specifier unchanged, and `files` ships `dist/` plus the generated or bundled data the code reads, nothing from `src/`.
- **Specs.** A spec is `*.spec.ts` and `npm test` runs `typecheck` first. An ES-module package keeps its specs beside their subjects in `src/` and runs them on the source: Node strips the types, which is why the source holds only erasable syntax (`verbatimModuleSyntax`, `erasableSyntaxOnly`). A CommonJS package compiles `export =` and `import` to `require`, which Node cannot run from source, so its `test` builds first and its specs (in `test/`, an ES-module folder) load the built `dist/` the way jest or prettier does. A package with nothing to build (`tsconfig`) keeps its spec at its root.
- **Paths.** A file found through `import.meta.url` or `__dirname` is resolved from the package root, which sits one level above both `src/` and `dist/` at the same depth, so one relative path works from the source and from the build.
- **CI.** `.github/workflows/ci.yml` installs and builds every package in folder order, then tests every package.

- `eslint-canon-fe` (`@starci/eslint-canon-fe`): the universal front-end ESLint canon (`starciFeConfig`, `loadHfs`) for TypeScript and Next.js; consumed by the `fe/eslint.config.mjs` of every StarCi app, beside its Grammar family config.
- `eslint-canon-be` (`@starci/eslint-canon-be`): the back-end ESLint canon (`starciBeConfig`, `loadHfs`) for Nest; consumed by the `be/eslint.config.mjs` of every StarCi app.
- `grammar` (`@starci/grammar`): the Grammar an app's UI is drawn in: the Common contract and the two families `core` and `offset-pop`, each with its root and stylesheet; consumed by every StarCi front end.
- `eslint-grammar-core` (`@starci/eslint-grammar-core`): the `core` family's lint factory (`coreGrammarConfig`) over the Grammar component API; versioned with `grammar`, with `@starci/eslint-canon-fe` as its peer.
- `eslint-grammar-offset-pop` (`@starci/eslint-grammar-offset-pop`): the `offset-pop` family's lint factory (`offsetPopGrammarConfig`), inheriting the core checks; versioned with `grammar`, with `@starci/eslint-grammar-core` as its peer.
- `stylelint-canon` (`@starci/stylelint-canon`): the CSS canon (Grammar tokens only, brand values only in `brand.css`); consumed by the `stylelint.config.mjs` of StarCi front ends.
- `heroicons` (`@starci/heroicons`): the glyphs `@heroicons/react` lacks, drawn in its style; imported by StarCi front ends.
- `event-stream` (`@starci/event-stream`): the server-sent-events client (Bearer renewal, Last-Event-ID resume, backoff, heartbeat, an SWR adapter); one instance per front end.
- `hfs` (`@starci/hfs`): the implementation behind `starci app` (scaffold, sync, check, lint, stack, db, codemod) for one product repository, run in-process by the harness CLI (`starci-harness`, `cli/`), which is the command line a product installs; `@starci/cli`, the app CLI that used to run it, is retired.
- `tsconfig` (`@starci/tsconfig`): the strict TypeScript presets `base`, `be`, `build`, `next` and `e2e`; extended by the tsconfig files of every StarCi app's back end and front end.
- `prettier-config` (`@starci/prettier-config`): the one Prettier config; consumed by every StarCi app's `prettier` setting.
- `jest-preset` (`@starci/jest-preset`): the jest config of a Nest repository and the shared unit-test double kit; consumed by the jest config and unit specs of StarCi back ends.
- `test-world` (`@starci/test-world`): the shared e2e world of every StarCi back end; pairs exactly with `@starci/jest-preset`.
- `ai-router` (`@starci/ai-router`): a NestJS module (`AiRouterModule.register` / `registerAsync`, the injectable `AiRouterService`) that routes OpenAI-compatible `chat`, `stream` and `embeddings` calls across many keys, models and providers, with breakers, rate-limit awareness, failover and redacted telemetry, and `@starci/ai-router/testing` (the fake provider and `AiRouterTestingModule`) for consumers' tests; its `npm test` also typechecks and lints, and fails under 90% line coverage.
