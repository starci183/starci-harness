# Inbox dedupe and client receipts

How a repeated delivery (a webhook, a job redelivery, a retried operation) becomes a no-op instead of a second
charge, message or transition: one inbox owned by `platform/inbox`, claimed in the receiver's own transaction.

## BE-IDEMPOTENCY-1 The receiving service claims the delivery before it acts

A domain service method that takes a delivery injects `@InjectInbox() private readonly inbox: Inbox` and, inside its
transaction, first awaits `this.inbox.claim(source, eventId, manager)` (with the receipt when it records one),
returning when the answer is `false`. `source` names the door or publisher; `eventId` is the sender's id of the
delivery (or a stable key derived from the operation), never generated by the receiver. The claim, the domain writes
and the outbox rows commit or roll back together; doors claim nothing.

Why: a sender without a timely answer resends; a claim in the effect's transaction makes effect and claim one atomic
fact.

```ts
await this.entityManager.transaction(async (manager) => {
    if (!(await this.inbox.claim(PROVIDER, deliveryId, manager, { insert: INSERT_RECEIPT, payload: body }))) return
    await this.outbox.write(manager, DELIVERY_QUEUE, { deliveryId }, { dedupeKey: `${DELIVERY_QUEUE}:${deliveryId}` })
})
```

Enforced by: `inbox-dedupe-required` (R80), `infra-needs-injector` (R85).

## BE-IDEMPOTENCY-2 The inbox is one table, owned by platform

`platform/inbox` owns one claims table keyed by `(source, event_id)`, created by a migration of the app, and inserts
with `ON CONFLICT DO NOTHING RETURNING`: `true` for a new pair, `false` for a duplicate, without aborting the caller's
transaction. A provider receipt table is written by the same claim through its `insert`. No capability creates another
dedupe table.

Why: one owner keeps "claims at most once" in one place, and the conflict-safe insert holds under concurrent delivery.

Enforced by: `inbox-dedupe-required` (R80), `schema-owner` (R35).

## BE-IDEMPOTENCY-3 An effectful client command marked `Effectful()` replays its committed outcome

An app declaring `idempotency` marks each effectful client command with `Effectful()` of `platform/inbox` and gives it a
required, bounded `idempotencyKey`; the domain service returns `inbox.runClient({ principalId, operation,
idempotencyKey, request }, manager, effect)`, which replays the stored outcome of a matching repeat and refuses a reused
key with a different request (`IDEMPOTENCY_KEY_REUSED`). Without the pattern, a public operation that takes an
`Idempotency-Key` binds it in its own domain table under a unique key.

Why: a timeout leaves a client unsure whether a mutation committed; the receipt binds the intent to its durable result.

Enforced by: `mutation-idempotent` (R310, judges marked commands), R155.
