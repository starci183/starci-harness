# Project anatomy

The canonical tree of an app, one per edition (`lite`, `full`) and place (the app root, `be/`, `fe/`). Every line is
generated from [hfs/slots.yaml](../hfs/slots.yaml): the path, the slot that owns it, its presence in that edition, the
pattern topics that teach it (their front matter) and the rules of [hfs/rules.yaml](../hfs/rules.yaml) that judge it,
each with the enforcers of its side (kind, then rule id). Nothing below the marker is written by hand; this page only
says why the tree has this shape.

## Why the tree is shaped this way

- **One repository, one app root.** Everything both sides share sits at the root: the one manifest and lockfile,
  `hfs.json`, CI, hooks, the stacks and the Work (`.starciwork`) of every side. A side holds its own code and its own
  tool configuration only; a root file inside a side is refused (`repo.side-root-forbidden`, Work in a side is
  `HFS_WORK_IN_FE` of R01). One root means one place to declare, install, gate and record a feature that spans both sides.
- **Owners before files.** A back end is apps that compose, features that receive a trigger, and modules (domain,
  platform, integrations, events, queues, projections) that features use, in the direction of the tier matrix
  (`tiers` in slots.yaml; why: [BE-ARCHITECTURE-1](../code/be/architecture.md)). A front end is a Next app whose
  `src/` splits routes, features, components, hooks and modules for the same reason
  ([fe/architecture](../code/fe/architecture.md), [fe/folder](../code/fe/folder.md)). A path names its owner,
  so a lint rule can judge an import by where its two ends live.
- **Editions differ in presence, never in shape.** Lite and full share one code structure; lite changes a slot's
  presence or its contents, and the slot's `editionWhy` says why. The two trees therefore differ only in a presence
  word or in the refused list, which is how to read a lite-versus-full difference at a glance.
- **Refused paths are part of the anatomy.** A slot that is `forbidden` or `external` names a mistake the gates refuse
  (a second tool config, an agent's scratch output, a plaintext secret); its `goesTo` in slots.yaml, where present, says where the
  thing belongs instead.

A rule shown as `CODE (no rule)` is a finding code a slot cites that rules.yaml does not define: a defect of hfs,
repaired in those two files, never here.

## Regenerating and the drift check

`starci contexts anatomy --write` rewrites the block between the markers; `starci contexts anatomy --check` exits 1
when this file differs from what the generator would write (`cli/src/core/contexts/anatomy.ts`, a runtime-only verb).
Change a slot, a rule or a pattern's front matter, then regenerate in the same commit.
