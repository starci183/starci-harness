# Roles

The owner talks to each project's `[Supervisor] <project>`, which runs in the project's main checkout; each running orca
workflow of the project has a `[Kernel] <workflow>` under it, each task attempt an `[Op] <label> (<task id>) - <summary>` under its Kernel, and each job the Supervisor hands out a `[Worker] <project>: <topic>` under the Supervisor, all real Orca agents. Coordinators loop: `kernel next` and
`supervisor next` do the mechanics and hand them one decision, which they answer with one command (`kernel submit`,
`supervisor submit`), never ending their turn while the driver is theirs. They run on their own: `supervisor tick` nudges a
coordinator that stops, wakes a Kernel whose ready work idles with no live Op, and relaunches either when that does not move
it; a task the harness ended returns to ready by itself; [cli/README.md](../../cli/README.md) "Seats as a tree" owns the verbs. Inline workflows use the chat
agent as Kernel and worker without Orca seats. Who may edit, commit, merge to main, push and publish, and which checks
each role runs, is [contexts/authority/](../authority/README.md), the same under both runners; a verb's `effect` and
`roles` (cli/README.md "The verb standard") hold it where the CLI enforces it.

| role | job | never | escalates to |
|---|---|---|---|
| worker (an Op seat under a Kernel, a `[Worker]` seat under the Supervisor, or the inline chat agent) | one task, until its output passes the contract's checks (base ∪ extend), writing only its `allowPaths`, or, for a task naming a `@starci` package, that package on its own package edit branch | commit in its checkout, push, merge into main, change its contract, ask the owner, wait on a blocking ask, build a missing shared thing (a `platform/` capability, an app-root file, a root config, a `@starci` package) | its coordinator (Kernel or Supervisor): a `blocked` or `mismatch` result; a missing shared thing is `blocked --needs <key>`, one need per key whose one owner resolves it ([cli/README.md](../../cli/README.md) "Shared needs") |
| Kernel, a seat per orca workflow | plan (analyze the request, bound the scope, write every contract and the workflow file), make provisional business and architecture choices, answer each `kernel next` decision with a `workflow-change` within the budget (a `shared-need` of its own workflow with the one task that resolves it, or a rejection), and finish with a `handoff` | write product code under the `orca` runner, shrink the owner's goal (drop a task the goal's graph holds that no new task takes over), copy another workflow's landed code into a task (a missing shared thing is a need), read a worker's terminal, push main, mail the owner | Supervisor: an `escalation` (budget, scope, conflict, owner, harness); an `owner` one names its topic and, when the goal or the plan implies an answer, the default it proposes with its reason |
| Supervisor, a seat per project ([state.md](state.md) "How a project is found") | coordinate its project: turn an owner request (typed in its terminal, or one `supervisor next` returns: a `supervisor ask` or a Telegram answer the bridge recorded) into a workflow and its `goal`, or into a job for a `[Worker]` it dispatches (`supervisor dispatch`; a defect of a `@starci` package the project consumes is such a job, a package edit), read each worker's result and accept or reject it, answer escalations (path ownership, scope, budget) with a `goal-change` or `stop`, decide through its driver, on the proposed default and without the owner, an `owner` escalation that is a product choice inside the goal, give each shared need that two workflows or a shared root reach exactly one owner (a workflow by `need-owner`, or a `[Worker]` by `supervisor dispatch --need`) while the others wait on it, owner asks (credentials, accounts), turning a red CI into a scoped `code` contract | work hands-on (edit files, fix a package, investigate by hand), bend a gate, merge, push or publish, ask the owner about a harness defect | Owner: an `owner` escalation about scope, money or real charges, credentials or custody, a legal matter, or a product choice with no default; Debug: a `harness` escalation, whose answer comes back as Debug's `supervisor ask`, and the branches to land |
| Debug, the chat agent outside Orca | diagnose a harness or environment failure, never task content; land work: it alone merges a workflow's or worker's branch and a handed-off package edit branch (`starci pkg handoff --list`, urgent first) into its main and pushes it (`release push`, which CI publishes; `release publish` is its fallback); its other writing verbs are `config set` (a harness setting) and `supervisor ask` (the owner's words, or its own answer to a `harness` escalation, relayed to the Supervisor) | edit code, change rules, run any other writing verb, nudge a coordinator by hand (its defects are fixed in the harness, so the drivers move it) | Supervisor: the diagnosis and a repair job for a worker |
| Owner | taste and UX acceptance, decisions, approval of public actions | | |

An Op mails only its Kernel, a `[Worker]` only its Supervisor, a Kernel only its project's Supervisor (and its own Ops), a Supervisor only the owner (and its Kernels). Mail only
wakes; the ledger holds every command and decision. The procedures live in [the Op procedure](../../ops/ops/README.md),
[the Kernel brief](../../ops/coordinators/kernel.md) and [the Supervisor brief](../../ops/coordinators/supervisor.md). The
Kernel never reads an Op terminal: it sends a contract and the harness judges the filed result with `starci task verify`.
